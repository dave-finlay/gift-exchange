# A Critical certifi Advisory That Dependabot Missed

Status: open, as of 2026-10-23. Grype caught it within a day; Dependabot
hasn't raised an alert or opened a pull request. certifi hasn't been
updated yet, deliberately, while we find out why.

## Summary

On 2026-10-20 GitHub published a critical advisory for certifi,
[GHSA-6q48-6c7w-9gw2](https://github.com/advisories/GHSA-6q48-6c7w-9gw2):
it bundles emSign root certificates whose intermediate CA keys were
compromised. Affected: `>= 2019.03.09, < 2026.10.19`. We had 2026.7.22,
an indirect dependency (django-anymail → requests → certifi), used when
the app calls Brevo's API over HTTPS.

The next daily image run found it, failed its gate, and stopped
publishing. That's the scanning half of the loop working. The fixing
half didn't start: GitHub raised no Dependabot alert, so no security
update followed.

Nothing was exposed: the app isn't deployed yet.

## What Worked

- The daily run found a new vulnerability in an image nobody had
  changed, which is what it's for.
- The gate failed on it (critical, with a fix) and the run didn't
  publish. The last good image, from 2026-10-20, stayed in the registry.
- The finding went to the Security tab with the version and the path it
  was found at.

## What Didn't

No Dependabot alert, so no Dependabot security update. These were
checked on 2026-10-23 and are all as they should be:

- The advisory is GitHub-reviewed (only reviewed advisories raise
  Dependabot alerts), for the `pip` ecosystem, and not withdrawn.
- The advisory database's own lookup (`GET /advisories?ecosystem=pip&affects=certifi@2026.7.22`)
  names this advisory, and none for our other 28 locked packages.
- Dependabot alerts and Dependabot security updates are both on.
- The dependency graph lists certifi 2026.7.22, depended on by requests.
- There are no Dependabot alerts in any state (open, dismissed,
  auto-dismissed or fixed), so it wasn't raised and then filtered out.
  This repository has never had a Dependabot alert, so we don't know
  whether alerts work here at all.
- Dependabot's jobs haven't failed; none has run since 2026-10-20 17:48,
  before the advisory.

## Why, Possibly

Unconfirmed. GitHub's list of ecosystems the dependency graph supports
has pip and Poetry for Python, not uv. Our graph isn't built by GitHub
reading `uv.lock`; a Dependabot job ("Configured Graph Update: uv")
submits it. The guess is that new advisories aren't matched against
graphs built that way, or only when the graph next updates. uv's docs
say some uv use cases with Dependabot "are not yet working". No GitHub
issue describing exactly this was found.

The graph has updated only after pushes that changed `pyproject.toml`
or `uv.lock` (2026-10-20 at 01:06, 01:08 and 17:48), not after pushes
that changed other files (17:48 a few seconds later, 18:32).

## Next Steps

1. A push to `main` that changes `pyproject.toml` or `uv.lock` without
   updating certifi, to see whether a fresh graph update raises the
   alert. A push that touches neither probably won't run a graph update,
   so it won't tell us anything.
2. Run the weekly uv version update by hand (Insights → Dependency
   graph → Dependabot → "Check for updates"). If it opens a certifi pull
   request, the update path works and only alerts are missing. If it
   doesn't, `lockfile-only` may not update indirect dependencies.
3. If neither raises an alert, ask on GitHub Community.
4. Then update certifi (`uv lock --upgrade-package certifi`), by
   Dependabot's pull request or by hand.

## Findings So Far

- Grype is pulling its weight. Without it, a critical in a shipped
  dependency would have gone unnoticed, since Dependabot said nothing.
- Don't rely on Dependabot alerts alone for a uv project until we know
  why this happened.
- A failed gate stops publishing, quietly. Three days of failed daily
  runs came to light only when we looked. GitHub emails a scheduled
  run's failure to whoever last changed the schedule; once the image is
  deployed, check that's enough, since a failed gate also means no
  redeploy.
